# VAXBRIDGE AI

**Every missed dose becomes an actionable next step.**

A full-stack prototype for closing immunisation-record gaps: discover a gap, classify whether it is
a genuinely missing dose or an incomplete record, explain the reasoning, prioritise the follow-up
work, turn it into a task, and resolve it — with every step auditable.

> ### Read this first
>
> **This is a prototype demonstration. It is not a government system.**
>
> - It is **not connected to, integrated with, endorsed by, or affiliated with** CoWIN, U-WIN, ABDM,
>   the Ministry of Health & Family Welfare, or any other official immunisation registry. No such
>   integration exists in this codebase, and none is implied.
> - **All data is synthetic.** The 37 patients, 365 vaccination events and every document are
>   generated by a deterministic seed script. No real person's health data is present.
> - **No clinical-accuracy, uptime, adoption or outcome statistics are claimed anywhere**, because
>   none have been measured. Where the UI shows a number, it is computed from this demonstration
>   database and labelled as such.
> - **No regulatory-compliance claim is made.** There is no certification, audit or approval behind
>   this code.
> - Document extraction runs in a **labeled demonstration mode** using fixed fixtures. No OCR
>   service is connected.
> - Credentials in this file exist **only** for this demo. Never reuse them.

## The core idea

Immunisation records fail in a specific way. A child's card is lost, a family moves between states,
a dose is given at a private clinic that never reports back, or a data-entry clerk types `05/03`
meaning May rather than March. The result is a record that is **incomplete**, not a child who is
**unvaccinated** — and systems that treat those as the same thing cause real harm: a dose gets
repeated, or a family gets labelled non-compliant.

VAXBRIDGE AI is built around one rule that follows from this:

> **A missing row in the database is never treated as proof that a dose was not given.**

Concretely, that rule shows up as:

- Every recommendation for a dose that is not up to date says *"no verified record exists"* — never
  *"not vaccinated"* — and carries an explicit caveat about checking the paper card and previous
  facilities.
- An **unverified** entry is a distinct state. It is not counted as a dose given, and not counted as
  a dose missed. It is counted as *something a human must resolve*.
- Detection of duplicates and conflicting dates is **read-only**. Nothing is merged, corrected or
  deleted automatically. Suspected duplicates never cause history to be deleted.
- Conflicting submissions are routed to a review queue. The stored record is left untouched.
- A caregiver's refusal or a family's migration is recorded as a **factual outcome** that changes how
  follow-up happens. It is never a penalty, never a "non-compliant" flag, and never blocks care.

The engine is **deterministic rules**, not a language model. There is no LLM anywhere in this
codebase. Prioritisation is reproducible, and the factors and weights behind each score are stored
so a ranking can be audited. A priority score is **operational triage** — it ranks follow-up work.
It is not a medical-risk prediction and must not be read as clinical judgement.

## Architecture

| Layer | Technology |
| --- | --- |
| API | Python 3.11, FastAPI, SQLAlchemy 2, Pydantic v2, Alembic |
| Database | SQLite (file-backed). `DATABASE_URL` switches to PostgreSQL without code changes |
| Auth | JWT (HS256) via `python-jose`, passwords hashed with `bcrypt` directly |
| Web | Next.js 14 (App Router), React 18, TypeScript, Tailwind CSS |
| 3D | Three.js via `@react-three/fiber` + `@react-three/drei` |
| Charts | Recharts (2D, for real data — the 3D scene is decorative and never encodes data) |

**Size:** ~9,400 lines of Python (application + tests), ~12,400 lines of TypeScript/TSX, 25 database
tables, 3 Alembic migrations, 72 API operations (43 GET / 21 POST / 8 PATCH), 29 web routes.

The API is the authority. The front end never decides authorization — it mirrors the server's
capability sets **for display only**, so the interface does not offer a destination the server will
refuse. Hiding a link is treated as a courtesy, never as a control; every request is re-checked
server-side.

### The 3D hero

The landing scene is real WebGL (protective sphere, DNA helix, connection lines, data nodes,
particles, luminous core, pointer-driven camera drift). It degrades deliberately:

- a static fallback renders while the bundle loads or if WebGL is unavailable;
- `prefers-reduced-motion` disables animation;
- a visible pause control stops the scene;
- a React error boundary catches a GPU/context failure and swaps in the static artwork instead of
  taking the page down.

### The sign-in scene

`/login` carries its own, deliberately smaller composition (`LoginScene3D`): a bevelled extruded
medical cross inside a luminous protective shell, with two orbiting data rings and 70 particles. It
sits beside a form people need to read, so it is calmer than the hero — lower particle count, a
capped `dpr` of 1.6, an autorotate slow enough not to pull the eye, and it stops rendering entirely
when off-screen or under reduced motion. A pure CSS/SVG `LoginSceneFallback` renders behind the same
error boundary.

The screen is a single viewport with no scrolling: brand, tagline and scene on the left, a compact
card on the right whose six demonstration accounts live in a `<select>` so none of them require
scrolling to reach. Below `lg` it collapses to one column. The scene is imported with
`dynamic(..., { ssr: false })`, which keeps three.js out of the sign-in critical path — `/login`
ships 9.48 kB (120 kB first load) and its chunk contains no reference to `WebGLRenderer`.

## Production deployment

Two documents cover this in full: **[docs/AUDIT.md](docs/AUDIT.md)** grades every
feature A–E against the file that proves it, and
**[docs/DEPLOYMENT.md](docs/DEPLOYMENT.md)** records what is provisioned and the
one step that needs an account owner.

```
                    Vercel project "vaxbridge"  — one origin
Browser ──┬── /          Next.js 14 (apps/web)
          └── /api/v1/*  Python serverless function (api/index.py)
                          └─ FastAPI ASGI, apps/api/app
                             ├─► Supabase PostgreSQL 17, role vaxbridge_app (DML only)
                             └─► Supabase Storage, private bucket, 5-minute signed URLs
```

**One origin is deliberate.** Hosting the frontend and the API on different
hostnames makes the session cookie third-party, which is the condition that
produced this project's recurring login failure. `next.config.mjs` proxies
`/api/v1/*` only when an API origin is explicitly configured, so production can
no longer ship a `http://localhost:8000` URL.

The application runs in two modes, and **mode A never depends on a paid key**:

| | Mode A — core | Mode B — enhanced |
|---|---|---|
| Trigger | default | a provider key is configured |
| Auth, patients, vaccinations, scheduling, inventory, analytics, appointments, audit, notifications, offline capture | full | full |
| Documents | upload, persist, retrieve, human review | same |
| Extraction | demo fixture, or real Tesseract where the binary exists | same, plus optional model-assisted interpretation |
| Insights | `/api/v1/insights` — deterministic, always available | same |
| Generative Q&A | reports unavailable, returns the real records anyway | `/api/v1/ai/ask`, grounded only on retrieved rows |

`GET /api/v1/health` reports the database backend, whether it persists across a
restart, the storage backend and its durability, and which OCR provider will
actually run. It never returns a connection string.

### Useful environment variables

| Variable | Default | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | `sqlite:///./vaxbridge_demo.db` | Any SQLAlchemy URL |
| `VAULT_SECRET_KEY` | dev fallback | JWT signing — **set this in any real deployment** |
| `VAULT_RECORD_SECRET` | falls back to the above | HMAC secret for signed record QR payloads |
| `RECORD_TTL_SECONDS` | `2592000` (30 days) | How long a signed record link stays valid |
| `OCR_DEMO_MODE` | `true` | Runs the labeled fixture extractor |
| `UPLOAD_DIR` | `./uploads` | Where uploaded documents are written |
| `RATE_LIMIT_DEFAULT` / `RATE_LIMIT_AUTH` | 600 / 60 | Requests per 60-second window |
| `TRUST_PROXY_HEADERS` | `1` | Honour `X-Forwarded-For` when identifying clients for rate limiting |
| `SESSION_COOKIE_NAME` | `vaxbridge_session` | Name of the httpOnly session cookie |
| `SESSION_COOKIE_SECURE` | `true` | `true`/`false`, or `auto` to derive from `X-Forwarded-Proto` |
| `SESSION_COOKIE_SAMESITE` | `none` | `none` is required for the app to work inside a cross-site iframe |
| `AUTH_DIAGNOSTICS` | `1` | Log the stage at which an authentication was rejected |
| `NEXT_PUBLIC_API_URL` | *(empty)* | Empty means "same origin", proxied by `next.config.mjs` |

Two of these deserve a note.

**`RATE_LIMIT_AUTH` is 60, not 20.** This service normally sits behind a reverse proxy that presents
every request from one loopback address, so an IP-keyed bucket is shared by everyone reaching the app
through it. At 20/minute a handful of sign-in retries by one person could lock out every other user
of the instance. 60/minute still makes online password guessing impractical. The per-account
throttling that would allow a lower figure again is **not implemented** and is listed under
[What is *not* implemented](#what-is-not-implemented).

**`TRUST_PROXY_HEADERS` is on by default** because without it every client behind the proxy shares a
single rate-limit bucket. Honouring `X-Forwarded-For` from an *untrusted* peer would let a caller
rotate the header and get a fresh bucket per request, so this must be turned off if the API is ever
exposed directly to the internet rather than behind a proxy that sets the header itself.

### Resetting the demonstration data

```bash
cd apps/api
rm -f vaxbridge_demo.db
DATABASE_URL="sqlite:///./vaxbridge_demo.db" python3 -m alembic upgrade head
python3 -c "from app.main import _ensure_seed_data; _ensure_seed_data()"
```

## Authorization model

Server-side, in `apps/api/app/rbac.py`, as capability sets. The web client mirrors them in
`src/lib/capabilities.ts` for display only.

| Capability | clinic_admin | public_health_admin | healthcare_worker | system_admin | patient | caregiver |
| --- | :-: | :-: | :-: | :-: | :-: | :-: |
| Clinical read | ✓ | ✓ | ✓ | — | own | authorized only |
| Clinical write | ✓ | — | ✓ | — | — | — |
| Patient management | ✓ | ✓ | ✓ | — | — | — |
| Outreach view / manage | ✓ | ✓ | ✓ (assigned only) | — | — | — |
| Inventory view | ✓ | ✓ | ✓ | — | — | — |
| Inventory manage | ✓ | — | ✓ | — | — | — |
| Analytics view | ✓ | ✓ | ✓¹ | — | — | — |
| Record review | ✓ | ✓ | ✓ | — | — | — |
| Caregiver management | ✓ | ✓ | — | — | — | — |
| User management | ✓ | — | — | ✓ | — | — |
| Audit view | ✓ | ✓ | — | ✓ | — | — |

¹ Healthcare workers can read analytics except `coverage-by-area`.

Two properties are deliberate and tested:

- **`system_admin` is in no clinical capability set.** Administering the platform does not grant
  access to patient health data. Clinical list endpoints return an empty set for that role
  (fail-closed), and analytics return 403.
- **Scoping fails closed.** Where a caller's authorized patient set cannot be determined, the query
  is filtered to match nothing rather than falling through unfiltered. An earlier version of this
  code leaked the entire outreach queue to the `patient` role that way; it is now a regression test.

Patient self-service is restricted to `full_name`, `phone` and `language`. A user cannot set their
own `is_active`, role, or any clinical field.

### Account provisioning

Public self-registration (`POST /api/v1/auth/register`) accepts only the **`patient`** and
**`caregiver`** roles — the two whose reach is confined to the person's own record, or to dependents
a clinic has explicitly authorized. Any other role is refused with 403, and an unrecognized role
with 400.

This is enforced on the server, not in the form. Before the guard existed, the endpoint accepted
whatever `role` appeared in the request body: posting `{"role": "clinic_admin"}` returned a token
with read/write access to all 37 seeded patients. Restricting the dropdown would not have fixed it,
because the request is plain JSON. `test_security.py` now asserts that every privileged role is
refused, that no account row is created by a refused attempt, and that a freshly registered
`patient` or `caregiver` sees zero patients.

Staff and administrative accounts are created by a holder of `USER_MANAGE` (`system_admin`,
`clinic_admin`) through `POST /api/v1/users`, which validates the role, rejects duplicate emails,
and writes an audit event naming the provisioner. A newly registered caregiver starts with no
dependents; each link must be authorized individually before any record becomes visible.

Accounts created in this build are **not email-verified** (`is_verified=False` for self-registration).
Nothing depends on that flag yet, and the registration page says so rather than implying a
confirmation email is on its way.

### Session architecture

A session is a JWT signed with `VAULT_SECRET_KEY` (HS256, 30-day expiry). It reaches the server by
**either** of two credentials, tried in this order:

1. `Authorization: Bearer <token>` — the documented API contract, used by scripts and tests.
2. `vaxbridge_session`, an **httpOnly** cookie set by `POST /auth/login` and `/auth/register`.

`get_current_user` in `app/deps.py` tries the bearer first and, if it fails to decode, falls back to
the cookie rather than rejecting outright. A client that cannot read its own storage may still be
presenting a stale token it cached earlier; treating that header as authoritative would sign the
user out for a bug they can neither see nor fix. Every rejected credential is logged with the branch
that rejected it (`AUTH_DIAGNOSTICS`, on by default), so the fallback is observable rather than
silent — while the response stays a single opaque 401, because which credential failed and why is
useful to an attacker and not to a client.

Cookie attributes are `HttpOnly; Secure; SameSite=None; Path=/`.

- **`SameSite=None`** because the app is normally opened inside an iframe on a different registrable
  domain from the one serving it. Requests the page makes to its own API are then *cross-site* in the
  SameSite sense — the site that matters is the top-level document's, not the iframe's — and a `Lax`
  cookie would be silently dropped from every `fetch`. `None` is honoured by browsers only together
  with `Secure`, hence both.
- **`HttpOnly`** so the token cannot be read by script, which makes it strictly harder to exfiltrate
  than a token in `localStorage`.
- Override with `SESSION_COOKIE_SECURE=0` and `SESSION_COOKIE_SAMESITE=lax` for a plain-HTTP
  deployment that is not framed by another site. `SESSION_COOKIE_SECURE=auto` derives the flag from
  `X-Forwarded-Proto`, but note that the Next.js rewrite proxy used here does **not** forward that
  header, so auto-detection cannot see the browser's real scheme and the default is explicit.

**Sign-in completes in one round-trip.** `POST /auth/login` returns
`{access_token, token_type, user}`, so the client never needs a second authenticated call to learn
who it is. That second call — to `/auth/me` — was where sign-in repeatedly broke: it was the first
request to depend on the client having stored *and replayed* the token, and in a browser that
refuses script-accessible storage it went out with no credential at all, turning an accepted
password into `401 "Not authenticated"`. `/auth/me` still exists and is still used to restore a
session on page load.

`src/lib/auth.ts` additionally wraps every `localStorage` access and verifies each write by reading
it back, falling back to in-memory storage for the tab. The app shell (`src/app/app/layout.tsx`)
always asks the server rather than requiring a locally readable token first, so a cookie-only
session survives a refresh.

**Sign-out calls `POST /auth/logout`.** JavaScript cannot delete an httpOnly cookie, so clearing only
the local token would leave the session alive and the next `/auth/me` would sign the user straight
back in. A stateless JWT cannot be revoked server-side without a deny-list, so the endpoint clears
the credential the browser will present and says plainly that the token itself expires on its own
schedule — it does not claim to have invalidated it everywhere.

### Authentication diagnostics

`AUTH_DIAGNOSTICS=1` (default) writes one line per rejected authentication to the server log, naming
the stage: `no_credentials`, `token_decode_failed`, `user_row_not_found`, `user_inactive`,
`authenticated_via_fallback`, and on the sign-in path `account_not_found`, `invalid_password`,
`account_disabled`, `token_generation_failed`. Each line carries the request path, User-Agent,
Origin, whether an `Authorization` header was present at all, and whether a session cookie was.

No secret material is logged: a token appears only as its length and a 12-hex SHA-256 prefix, which
cannot be reversed or replayed. Passwords and hashes are never logged. The user-facing message stays
`Invalid credentials` for both an unknown email and a wrong password, so the log cannot be used to
enumerate accounts through the API.

Set `AUTH_DIAGNOSTICS=0` to silence it.

## The gap-resolution engine

### 1. Discover → classify

`apps/api/app/scheduling/engine.py` evaluates every patient against the approved schedule version
and emits one recommendation per rule, with a status:

| Status | Meaning |
| --- | --- |
| `up_to_date` | A **verified** event satisfies the rule |
| `upcoming` | Not yet due |
| `due` | Due now, no verified record |
| `potentially_overdue` | A defined window has elapsed (only rules with `max_months` can produce this) |
| `verification_required` | An **unverified** entry exists — resolve the record before concluding anything |

Any unverified event for a vaccine downgrades a non-`up_to_date` status to `verification_required`.
Due dates are derived from the rule (`dob + 30.4375 × min_months`), never invented.

### 2. Explain

Each recommendation carries a stored, human-readable explanation generated by the rules engine, and
every non-`up_to_date` explanation states that *no verified record exists* and appends an explicit
caveat that this is not evidence a dose was not given. Tests assert those forbidden phrasings never
appear.

### 3. Prioritise

`apps/api/app/prioritization.py` scores follow-up work from four stored factors: due-date urgency,
record uncertainty, previous unsuccessful follow-up, and service opportunity (an upcoming
appointment plus usable stock). Factors and weights are persisted with the score, so a ranking can
be audited and recomputed. `POST /api/v1/outreach/{id}/prioritize` returns the score, band,
explanation and the disclaimer that this is triage, not medical-risk prediction.

### 4. Task → resolve

Outreach tasks carry a lifecycle (`open` → `in_progress` → `escalated` → `resolved`) validated
server-side, so an unknown status cannot corrupt the analytics buckets. Contact attempts are logged
with a controlled outcome vocabulary; `refused`, `migrated` and `deceased` are legitimate outcomes
that change how follow-up proceeds and carry no penalty. Reopening a resolved task clears its
resolution timestamp.

### 5. Document reconciliation

A separate path handles the case where evidence exists but is not yet trustworthy:

1. `POST /api/v1/documents/upload` stores the file and runs the **labeled demo extractor**.
2. Extracted fields land with `requires_review` flags and **no confidence value**, because the demo
   provider does not supply a calibrated one. The UI states this rather than inventing a number.
3. `POST /api/v1/extracted-fields/{id}/review` records a human decision. **It never creates an
   event.**
4. `POST /api/v1/documents/{id}/finalize` is the only path from document to clinical record. It
   refuses unless every field has a decision, the required fields are approved, the date is
   parseable and not in the future, the vaccine resolves against the controlled terminology, and no
   identical dose already exists (409). On success it writes exactly one verified event.

Vaccine resolution is dose-aware: loose substring matching previously mapped
`"Pentavalent, Dose 3"` to `PENTA1`. Ambiguous dates (`05/03/2024`) are flagged with the
alternatives rather than silently guessed.

### 6. Identity matching

`POST /api/v1/record-matches/detect` surfaces candidates with a score, the evidence that matched,
the fields that differ, and a recommended action. **Ambiguous identities are never auto-merged.**
Recording a decision never merges records and never deletes history — both are asserted in tests.

### 7. Analytics

Eight endpoints under `/api/v1/analytics/*`, each returning a `metric_definition` describing exactly
what is measured. Small-area suppression hides counts below 5 patients so a service area cannot be
re-identified. Every response names its data source as the demonstration database, and the UI states
that **completeness of registered patients is not population coverage** — these numbers describe the
records held, never the community.

## Offline capture

Field work happens where connectivity does not. `src/lib/offline.ts` implements an explicit local
queue rather than relying on background sync:

- A capture is validated **on the device, at the point of care** — a future date or a missing dose
  label is rejected while the worker is still with the family, not hours later.
- Each capture gets a stable client-generated id. The API is **idempotent** on it, so replaying a
  batch after an uncertain response cannot create a duplicate dose.
- Synced doses arrive as **unverified**. A field capture never silently confirms itself.
- Server outcomes are handled distinctly: `synchronized` and `deduplicated` leave the queue;
  `conflict_requires_review` leaves the queue (the server has taken custody) but is surfaced to the
  worker; `rejected` **stays, flagged, with the server's reason** — because retrying unchanged input
  cannot succeed and silently dropping a real capture would be worse.
- The patient and vaccine pickers are cached locally so capture still works with no signal. The
  cached list is labelled as cached, with its timestamp.
- A persistent bar in the app shell always shows connectivity and how many captures are waiting.
  Being offline never looks like being signed out.
- Syncing does **not** require a locally readable token. A missing one used to abort the upload and
  tell the worker to "sign in again" even when they were signed in — the session can live only in the
  httpOnly cookie, which JavaScript cannot read by design. The request is now attempted and the
  server decides; `no_session` is reported only on a real 401/403, and the batch is returned to
  `queued` so nothing is stranded or left looking permanently in flight.

**Where the queue lives.** `src/lib/persistent-store.ts` writes to IndexedDB
first, localStorage second, memory last — in that order because a cross-site
iframe blocks localStorage outright while IndexedDB is merely partitioned. The
offline module's API is synchronous and is called during render, so hydration
fills an in-memory mirror once at startup and writes persist in the background;
no consumer had to change. When neither store is available the UI says the queue
is memory-only and will be lost if the page closes, rather than implying a
captured dose is safe. Values written under the old localStorage-only queue are
adopted on first hydration, so an upgrade does not silently discard work already
in the field.

A service worker (`public/sw.js`) keeps the shell reachable: navigations are network-first, build
assets cache-first, and **`/api/` is never cached** — serving stale clinical data offline would be
worse than showing an error. It registers in production builds only.

In development it does the opposite: any installed worker is **unregistered and its caches deleted**.
A worker registered during a production run persists in the browser indefinitely — it survives
reloads, server restarts and rebuilds, and the page that registered it no longer has to exist for it
to keep controlling the origin. Since this component only ever registered in production, a dev
session would never have removed one, so a leftover worker keeps serving a cached app shell while the
source on disk has moved on. That failure is invisible and total: the served bundle verifiably
contains a fix, and the browser still runs the code from before it. Bumping the `VERSION` constant in
`sw.js` also purges stale caches from the outside, because the browser re-fetches that file
byte-for-byte and `activate` deletes every cache whose name does not match.

Notable things the tests assert, because they are easy to get wrong and easy to regress:

- No seeded dose is dated in the future, and none is dated before the patient's birth. Doses are
  derived from an explicit age-at-administration table rather than "days ago" offsets, which
  silently encode the wrong age.
- Recommendation explanations never claim a dose was not given.
- Outreach status buckets are mutually exclusive and sum to the total.
- A tampered QR payload is rejected; an expired one is rejected; the public verification endpoint
  discloses no name, date of birth or per-dose detail.
- Analytics returns 403 for `patient`, `caregiver` and `system_admin`.
- Confirming an identity match neither merges nor deletes.
- A rejected offline capture is never stored.

**Frontend verification** is TypeScript (`tsc --noEmit`, clean), a production `next build` (clean, no
warnings), and HTTP 200 checks across all 28 routes. **There are no automated browser tests** — see
below.

## What is *not* implemented

Stated plainly, because an honest gap list is more useful than a confident demo.

**External integrations — none exist.**

- No CoWIN, U-WIN, ABDM or any government registry integration. No API client, no credential, no
  stub pretending to be one.
- **OCR depends on what is installed.** `OCR_PROVIDER` selects between the labeled demo fixture,
  the open-source Tesseract engine, `none`, and `auto` (Tesseract when genuinely present, otherwise
  the fixture — and the document records which one ran). Tesseract is free, offline and needs no key,
  but the binary is **not installed in this environment and cannot be installed on Vercel's Python
  runtime**, so a serverless deployment falls back to the fixture and says so. Confidence is reported
  only when the engine supplies it; the fixture measures nothing and therefore reports `None`.
  `GET /api/v1/health` states the effective provider, so nobody has to guess.
- No SMS, WhatsApp, email or push provider. Notifications are in-app database rows only; nothing is
  ever delivered to a real device. The `/contact` form writes to `localStorage` and says so on the
  page.
- **No AI provider is called by default, and none is required.** `AI_PROVIDER` is `none` unless a
  key is configured. The optional seam supports OpenAI, Anthropic, Google and any OpenAI-compatible
  endpoint (including a local Ollama or vLLM, which needs no paid service at all). With no key,
  `POST /api/v1/ai/ask` returns `ai_available: false`, `text: null` and an explicit reason — but
  still returns the records it actually retrieved, because those were always real. Nothing is
  fabricated to fill the gap.
  `GET /api/v1/insights` is deterministic arithmetic over registry rows and is fully available with
  no key. It is labelled `engine: deterministic` and never described as AI. "AI" in the product name
  refers to the rules engine, which is deliberate: a scheduler must be reproducible, and no model may
  decide a dose.

**Clinical and data scope.**

- The schedule is a 14-rule demonstration sample, not the full National Immunization Schedule. It is
  marked `1.0.0-demo`.
- No drug-interaction, contraindication or allergy checking. No clinical decision support. A
  priority score is triage, not medical advice.
- Identity matching detects candidates but **implements no merge**. Confirming a match records a
  decision; it never combines records, which is the correct default for ambiguous identities but
  means a confirmed duplicate must still be reconciled by hand outside this tool.
- No deletion or correction workflow for a wrong dose beyond recording a conflicting submission for
  review.

**Platform and security.**

- **Local development still runs on SQLite.** A managed PostgreSQL 17 (Supabase project
  `gfoijsgtpenyspnqzcil`) is provisioned with the schema, 44 foreign keys and 39 query indexes
  applied, and the application connects to it through a least-privilege role with no DDL right. All
  25 models compile to Postgres DDL and the app contains no raw SQL. What has **not** happened is a
  full request-level test run against that instance: this sandbox has no network path to it, so the
  schema was applied and verified through the provider's own SQL interface rather than by exercising
  the ORM against it. `docs/DEPLOYMENT.md` records exactly what is and is not proven.
- No refresh tokens, no token revocation list, no MFA, no password reset, and no email verification
  on registration. `POST /auth/logout` clears the session cookie the browser will present, but a
  stateless JWT cannot be revoked without a deny-list: a token already copied elsewhere stays valid
  until it expires. The logout response says so rather than implying a full revocation.
- Rate limiting is in-memory per process: it resets on restart and is not shared across workers. It
  is keyed by client IP, and there is **no per-account throttling** — so many failures against one
  account from many IPs are not specifically impeded, and one client behind a shared address can
  exhaust the bucket for others. This is why `RATE_LIMIT_AUTH` is 60 rather than a tighter figure.
  On a serverless platform it is weaker still: each function instance keeps its own counters, so the
  limit is best-effort across a fleet. A hard guarantee needs a shared store or an edge-level limit.
- The session cookie is `SameSite=None; Secure; Partitioned`. `None` is required for the app to work
  inside a cross-site iframe, which also means it is sent on cross-site requests to this origin;
  `Partitioned` (CHIPS) keys the jar to the top-level site, which is what lets the cookie exist at all
  where third-party cookies are blocked. Where a browser supports neither, the bearer-token path, the
  in-memory fallback and the session handoff still work, and the sign-in page says which mode it is
  in. Deployed top-level on its own domain — the intended production shape — the cookie is
  first-party and none of this applies.
- **Uploads have two backends.** `STORAGE_BACKEND=local` writes to disk (the default, and not
  durable on serverless); `supabase` uses a private Supabase Storage bucket with 5-minute signed URLs,
  and is what the Vercel project is configured with. There is still **no virus scanning and no CDN**,
  and no asynchronous processing queue — OCR runs inside the request, bounded by `OCR_TIMEOUT_SECONDS`.
- The signed record QR is an HMAC over the summary using a server-side secret. It confirms
  integrity and expiry but it is **not** a public-key credential: there is no certificate chain, no
  issuer directory, and verification requires reaching this server. It is not recognised by any
  registry.
- The demo secret keys have development fallbacks. A real deployment must set them explicitly.

**Interface.**

- **English only.** A per-user language preference (including Hindi) is stored, but no translation
  ships. Earlier copy on the privacy page claimed a Hindi interface; that has been corrected to
  match reality.
- **No automated frontend tests.** No Playwright, Cypress or Jest suite exists. The UI is verified by
  type-checking, a clean production build and manual route/API checks — which is materially weaker
  than the backend's 429 tests.
- No real-time updates (no WebSocket or SSE). Pages fetch on load and on explicit refresh.
- Accessibility is implemented (semantic landmarks, focus states, `aria` attributes, reduced-motion
  support, keyboard-reachable controls) but has **not** been verified with assistive technology or an
  automated audit such as axe.
- The 3D scene is decorative and `aria-hidden`; it never encodes data. All data visualisation is 2D
  Recharts.

**Analytics.**

- Descriptive only. No forecasting, no epidemiological model, no extrapolation from the registered
  population to the general population — explicitly, because that inference is not licensed by this
  data.
- All figures describe the synthetic demonstration database. They must not be quoted as real-world
  statistics.
