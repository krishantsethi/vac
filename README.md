# VAXBRIDGE AI

**Every missed dose becomes an actionable next step.**

A full-stack prototype for closing immunisation-record gaps: discover a gap, classify whether it is
a genuinely missing dose or an incomplete record, explain the reasoning, prioritise the follow-up
work, turn it into a task, and resolve it — with every step auditable.

> ### Read this first
>
> **This is a prototype demonstration. It is not a government system.**
>
> - It is **not connected to, integrated with, endorsed by, or affiliated with** CoWIN, U-WIN, ABDM,
>   the Ministry of Health & Family Welfare, or any other official immunisation registry. No such
>   integration exists in this codebase, and none is implied.
> - **All data is synthetic.** The 37 patients, 365 vaccination events and every document are
>   generated by a deterministic seed script. No real person's health data is present.
> - **No clinical-accuracy, uptime, adoption or outcome statistics are claimed anywhere**, because
>   none have been measured. Where the UI shows a number, it is computed from this demonstration
>   database and labelled as such.
> - **No regulatory-compliance claim is made.** There is no certification, audit or approval behind
>   this code.
> - Document extraction runs in a **labeled demonstration mode** using fixed fixtures. No OCR
>   service is connected.
> - Credentials in this file exist **only** for this demo. Never reuse them.

## The core idea

Immunisation records fail in a specific way. A child's card is lost, a family moves between states,
a dose is given at a private clinic that never reports back, or a data-entry clerk types `05/03`
meaning May rather than March. The result is a record that is **incomplete**, not a child who is
**unvaccinated** — and systems that treat those as the same thing cause real harm: a dose gets
repeated, or a family gets labelled non-compliant.

VAXBRIDGE AI is built around one rule that follows from this:

> **A missing row in the database is never treated as proof that a dose was not given.**

Concretely, that rule shows up as:

- Every recommendation for a dose that is not up to date says *"no verified record exists"* — never
  *"not vaccinated"* — and carries an explicit caveat about checking the paper card and previous
  facilities.
- An **unverified** entry is a distinct state. It is not counted as a dose given, and not counted as
  a dose missed. It is counted as *something a human must resolve*.
- Detection of duplicates and conflicting dates is **read-only**. Nothing is merged, corrected or
  deleted automatically. Suspected duplicates never cause history to be deleted.
- Conflicting submissions are routed to a review queue. The stored record is left untouched.
- A caregiver's refusal or a family's migration is recorded as a **factual outcome** that changes how
  follow-up happens. It is never a penalty, never a "non-compliant" flag, and never blocks care.

The engine is **deterministic rules**, not a language model. There is no LLM anywhere in this
codebase. Prioritisation is reproducible, and the factors and weights behind each score are stored
so a ranking can be audited. A priority score is **operational triage** — it ranks follow-up work.
It is not a medical-risk prediction and must not be read as clinical judgement.

## Architecture

| Layer | Technology |
| --- | --- |
| API | Python 3.11, FastAPI, SQLAlchemy 2, Pydantic v2, Alembic |
| Database | SQLite (file-backed). `DATABASE_URL` switches to PostgreSQL without code changes |
| Auth | JWT (HS256) via `python-jose`, passwords hashed with `bcrypt` directly |
| Web | Next.js 14 (App Router), React 18, TypeScript, Tailwind CSS |
| 3D | Three.js via `@react-three/fiber` + `@react-three/drei` |
| Charts | Recharts (2D, for real data — the 3D scene is decorative and never encodes data) |

**Size:** ~9,400 lines of Python (application + tests), ~12,400 lines of TypeScript/TSX, 25 database
tables, 2 Alembic migrations, 65 API operations (40 GET / 17 POST / 8 PATCH), 28 web routes.

The API is the authority. The front end never decides authorization — it mirrors the server's
capability sets **for display only**, so the interface does not offer a destination the server will
refuse. Hiding a link is treated as a courtesy, never as a control; every request is re-checked
server-side.

### The 3D hero

The landing scene is real WebGL (protective sphere, DNA helix, connection lines, data nodes,
particles, luminous core, pointer-driven camera drift). It degrades deliberately:

- a static fallback renders while the bundle loads or if WebGL is unavailable;
- `prefers-reduced-motion` disables animation;
- a visible pause control stops the scene;
- a React error boundary catches a GPU/context failure and swaps in the static artwork instead of
  taking the page down.

## Running it

Two processes. The web server proxies `/api/v1/*` to the API, so the browser never needs to reach
port 8000 directly.

### 1. API

```bash
cd apps/api
python3 -m pip install -r requirements.txt -r requirements-dev.txt

# Create the schema and seed the demonstration data.
python3 -m alembic upgrade head
python3 -c "from app.main import _ensure_seed_data; _ensure_seed_data()"

python3 -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Interactive docs: <http://localhost:8000/docs>. Health: <http://localhost:8000/api/v1/health>.

### 2. Web

```bash
cd apps/web
npm install
npm run dev          # http://localhost:3000, binds 0.0.0.0
```

### Useful environment variables

| Variable | Default | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | `sqlite:///./vaxbridge_demo.db` | Any SQLAlchemy URL |
| `VAULT_SECRET_KEY` | dev fallback | JWT signing — **set this in any real deployment** |
| `VAULT_RECORD_SECRET` | falls back to the above | HMAC secret for signed record QR payloads |
| `RECORD_TTL_SECONDS` | `2592000` (30 days) | How long a signed record link stays valid |
| `OCR_DEMO_MODE` | `true` | Runs the labeled fixture extractor |
| `UPLOAD_DIR` | `./uploads` | Where uploaded documents are written |
| `RATE_LIMIT_DEFAULT` / `RATE_LIMIT_AUTH` | 600 / 20 | Requests per window |
| `NEXT_PUBLIC_API_URL` | *(empty)* | Empty means "same origin", proxied by `next.config.mjs` |

### Resetting the demonstration data

```bash
cd apps/api
rm -f vaxbridge_demo.db
DATABASE_URL="sqlite:///./vaxbridge_demo.db" python3 -m alembic upgrade head
python3 -c "from app.main import _ensure_seed_data; _ensure_seed_data()"
```

> **Reseeding invalidates every previously issued JWT** — user ids change. The web app confirms a
> token against `/auth/me` on load rather than trusting its local expiry claim, so a stale session
> returns you to the sign-in page instead of failing silently.

### Seeded demonstration database

37 patients across 6 service areas · 365 vaccination events (361 verified, 4 unverified) · 518
schedule recommendations · 14 vaccines · 14 schedule rules · 9 outreach tasks · 8 inventory batches ·
4 documents awaiting review · 1 identity-match candidate. The seed is deterministic
(`random.Random(20260131)`), so the same data is produced on every run.

## Authorization model

Server-side, in `apps/api/app/rbac.py`, as capability sets. The web client mirrors them in
`src/lib/capabilities.ts` for display only.

| Capability | clinic_admin | public_health_admin | healthcare_worker | system_admin | patient | caregiver |
| --- | :-: | :-: | :-: | :-: | :-: | :-: |
| Clinical read | ✓ | ✓ | ✓ | — | own | authorized only |
| Clinical write | ✓ | — | ✓ | — | — | — |
| Patient management | ✓ | ✓ | ✓ | — | — | — |
| Outreach view / manage | ✓ | ✓ | ✓ (assigned only) | — | — | — |
| Inventory view | ✓ | ✓ | ✓ | — | — | — |
| Inventory manage | ✓ | — | ✓ | — | — | — |
| Analytics view | ✓ | ✓ | ✓¹ | — | — | — |
| Record review | ✓ | ✓ | ✓ | — | — | — |
| Caregiver management | ✓ | ✓ | — | — | — | — |
| User management | ✓ | — | — | ✓ | — | — |
| Audit view | ✓ | ✓ | — | ✓ | — | — |

¹ Healthcare workers can read analytics except `coverage-by-area`.

Two properties are deliberate and tested:

- **`system_admin` is in no clinical capability set.** Administering the platform does not grant
  access to patient health data. Clinical list endpoints return an empty set for that role
  (fail-closed), and analytics return 403.
- **Scoping fails closed.** Where a caller's authorized patient set cannot be determined, the query
  is filtered to match nothing rather than falling through unfiltered. An earlier version of this
  code leaked the entire outreach queue to the `patient` role that way; it is now a regression test.

Patient self-service is restricted to `full_name`, `phone` and `language`. A user cannot set their
own `is_active`, role, or any clinical field.

## The gap-resolution engine

### 1. Discover → classify

`apps/api/app/scheduling/engine.py` evaluates every patient against the approved schedule version
and emits one recommendation per rule, with a status:

| Status | Meaning |
| --- | --- |
| `up_to_date` | A **verified** event satisfies the rule |
| `upcoming` | Not yet due |
| `due` | Due now, no verified record |
| `potentially_overdue` | A defined window has elapsed (only rules with `max_months` can produce this) |
| `verification_required` | An **unverified** entry exists — resolve the record before concluding anything |

Any unverified event for a vaccine downgrades a non-`up_to_date` status to `verification_required`.
Due dates are derived from the rule (`dob + 30.4375 × min_months`), never invented.

### 2. Explain

Each recommendation carries a stored, human-readable explanation generated by the rules engine, and
every non-`up_to_date` explanation states that *no verified record exists* and appends an explicit
caveat that this is not evidence a dose was not given. Tests assert those forbidden phrasings never
appear.

### 3. Prioritise

`apps/api/app/prioritization.py` scores follow-up work from four stored factors: due-date urgency,
record uncertainty, previous unsuccessful follow-up, and service opportunity (an upcoming
appointment plus usable stock). Factors and weights are persisted with the score, so a ranking can
be audited and recomputed. `POST /api/v1/outreach/{id}/prioritize` returns the score, band,
explanation and the disclaimer that this is triage, not medical-risk prediction.

### 4. Task → resolve

Outreach tasks carry a lifecycle (`open` → `in_progress` → `escalated` → `resolved`) validated
server-side, so an unknown status cannot corrupt the analytics buckets. Contact attempts are logged
with a controlled outcome vocabulary; `refused`, `migrated` and `deceased` are legitimate outcomes
that change how follow-up proceeds and carry no penalty. Reopening a resolved task clears its
resolution timestamp.

### 5. Document reconciliation

A separate path handles the case where evidence exists but is not yet trustworthy:

1. `POST /api/v1/documents/upload` stores the file and runs the **labeled demo extractor**.
2. Extracted fields land with `requires_review` flags and **no confidence value**, because the demo
   provider does not supply a calibrated one. The UI states this rather than inventing a number.
3. `POST /api/v1/extracted-fields/{id}/review` records a human decision. **It never creates an
   event.**
4. `POST /api/v1/documents/{id}/finalize` is the only path from document to clinical record. It
   refuses unless every field has a decision, the required fields are approved, the date is
   parseable and not in the future, the vaccine resolves against the controlled terminology, and no
   identical dose already exists (409). On success it writes exactly one verified event.

Vaccine resolution is dose-aware: loose substring matching previously mapped
`"Pentavalent, Dose 3"` to `PENTA1`. Ambiguous dates (`05/03/2024`) are flagged with the
alternatives rather than silently guessed.

### 6. Identity matching

`POST /api/v1/record-matches/detect` surfaces candidates with a score, the evidence that matched,
the fields that differ, and a recommended action. **Ambiguous identities are never auto-merged.**
Recording a decision never merges records and never deletes history — both are asserted in tests.

### 7. Analytics

Eight endpoints under `/api/v1/analytics/*`, each returning a `metric_definition` describing exactly
what is measured. Small-area suppression hides counts below 5 patients so a service area cannot be
re-identified. Every response names its data source as the demonstration database, and the UI states
that **completeness of registered patients is not population coverage** — these numbers describe the
records held, never the community.

## Offline capture

Field work happens where connectivity does not. `src/lib/offline.ts` implements an explicit local
queue rather than relying on background sync:

- A capture is validated **on the device, at the point of care** — a future date or a missing dose
  label is rejected while the worker is still with the family, not hours later.
- Each capture gets a stable client-generated id. The API is **idempotent** on it, so replaying a
  batch after an uncertain response cannot create a duplicate dose.
- Synced doses arrive as **unverified**. A field capture never silently confirms itself.
- Server outcomes are handled distinctly: `synchronized` and `deduplicated` leave the queue;
  `conflict_requires_review` leaves the queue (the server has taken custody) but is surfaced to the
  worker; `rejected` **stays, flagged, with the server's reason** — because retrying unchanged input
  cannot succeed and silently dropping a real capture would be worse.
- The patient and vaccine pickers are cached locally so capture still works with no signal. The
  cached list is labelled as cached, with its timestamp.
- A persistent bar in the app shell always shows connectivity and how many captures are waiting.
  Being offline never looks like being signed out.

A service worker (`public/sw.js`) keeps the shell reachable: navigations are network-first, build
assets cache-first, and **`/api/` is never cached** — serving stale clinical data offline would be
worse than showing an error. It registers in production builds only, so it cannot serve stale
bundles during development.

| `test_offline_sync.py` | 33 | Idempotency, conflicts, batch limits |
| `test_analytics.py` | 30 | Metric definitions, mutually exclusive buckets, suppression |
| `test_inventory.py` | 25 | Stock arithmetic, expiry, low-stock and transaction guards |
| `test_scheduling.py` | 25 | Rule evaluation, statuses, explanation wording |
| `test_data_integrity.py` | 18 | Population-wide invariants across the seeded data |
| **Total** | **331** | |

Notable things the tests assert, because they are easy to get wrong and easy to regress:

- No seeded dose is dated in the future, and none is dated before the patient's birth. Doses are
  derived from an explicit age-at-administration table rather than "days ago" offsets, which
  silently encode the wrong age.
- Recommendation explanations never claim a dose was not given.
- Outreach status buckets are mutually exclusive and sum to the total.
- A tampered QR payload is rejected; an expired one is rejected; the public verification endpoint
  discloses no name, date of birth or per-dose detail.
- Analytics returns 403 for `patient`, `caregiver` and `system_admin`.
- Confirming an identity match neither merges nor deletes.
- A rejected offline capture is never stored.

**Frontend verification** is TypeScript (`tsc --noEmit`, clean), a production `next build` (clean, no
warnings), and HTTP 200 checks across all 28 routes. **There are no automated browser tests** — see
below.

## What is *not* implemented

Stated plainly, because an honest gap list is more useful than a confident demo.

**External integrations — none exist.**

- No CoWIN, U-WIN, ABDM or any government registry integration. No API client, no credential, no
  stub pretending to be one.
- No live OCR provider. Extraction is three labeled fixtures. There is no confidence scoring,
  because the demo provider supplies no calibrated measure and inventing one would be worse than
  omitting it.
- No SMS, WhatsApp, email or push provider. Notifications are in-app database rows only; nothing is
  ever delivered to a real device. The `/contact` form writes to `localStorage` and says so on the
  page.
- No LLM or AI service is called anywhere. "AI" in the product name refers to the deterministic
  rules engine, which is deliberate: a scheduler must be reproducible.

**Clinical and data scope.**

- The schedule is a 14-rule demonstration sample, not the full National Immunization Schedule. It is
  marked `1.0.0-demo`.
- No drug-interaction, contraindication or allergy checking. No clinical decision support. A
  priority score is triage, not medical advice.
- Identity matching detects candidates but **implements no merge**. Confirming a match records a
  decision; it never combines records, which is the correct default for ambiguous identities but
  means a confirmed duplicate must still be reconciled by hand outside this tool.
- No deletion or correction workflow for a wrong dose beyond recording a conflicting submission for
  review.

**Platform and security.**

- SQLite, not PostgreSQL, in this environment. The code is database-agnostic and migrations are real,
  but no PostgreSQL instance was available to test against.
- No refresh tokens, no token revocation list, no MFA, no password reset, and no email verification
  on registration. Sessions end only at JWT expiry.
- Rate limiting is in-memory per process: it resets on restart and is not shared across workers.
- File uploads go to local disk with no object storage, no virus scanning and no CDN.
- The signed record QR is an HMAC over the summary using a server-side secret. It confirms
  integrity and expiry but it is **not** a public-key credential: there is no certificate chain, no
  issuer directory, and verification requires reaching this server. It is not recognised by any
  registry.
- The demo secret keys have development fallbacks. A real deployment must set them explicitly.

**Interface.**

- **English only.** A per-user language preference (including Hindi) is stored, but no translation
  ships. Earlier copy on the privacy page claimed a Hindi interface; that has been corrected to
  match reality.
- **No automated frontend tests.** No Playwright, Cypress or Jest suite exists. The UI is verified by
  type-checking, a clean production build and manual route/API checks — which is materially weaker
  than the backend's 331 tests.
- No real-time updates (no WebSocket or SSE). Pages fetch on load and on explicit refresh.
- Accessibility is implemented (semantic landmarks, focus states, `aria` attributes, reduced-motion
  support, keyboard-reachable controls) but has **not** been verified with assistive technology or an
  automated audit such as axe.
- The 3D scene is decorative and `aria-hidden`; it never encodes data. All data visualisation is 2D
  Recharts.

**Analytics.**

- Descriptive only. No forecasting, no epidemiological model, no extrapolation from the registered
  population to the general population — explicitly, because that inference is not licensed by this
  data.
- All figures describe the synthetic demonstration database. They must not be quoted as real-world
  statistics.
